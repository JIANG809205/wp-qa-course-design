# 大模型实测结果（v2 修正版）

> 修正说明：v1 的表格里除"与人工重合"外全是 100%，经复核是**度量方法过松**造成的虚高，不是模型能力。
> 本版重写全部指标，并对归因任务改用 12 条"去提示"难样本重测。原始数据：`outputs/metrics-v2.json`、`outputs/triage-hard.json`。

---

## 一、为什么 v1 不可信（四个度量缺陷）

| v1 指标 | v1 实现 | 缺陷 | 后果 |
|---|---|---|---|
| 字段完整 100% | 只判断 6 个 key 是否存在 | 不校验类型、不校验 steps 是否为空数组、不校验 expected 是否有实质内容 | 空壳用例也算"完整" |
| 脚本结构 OK 100% | 大括号配对 + 含 "assert" 字样 | 注释里写 assert 也算；不校验类声明、不校验 URL | 根本跑不了的代码也算"OK" |
| 含断言 100% | 子串匹配 "assert" | 不区分强断言/弱断言，不看断言对象是否真实存在 | 断言写在幻觉元素上也算 |
| 归因准确率 100% | 5 条日志，且**把结论写进了日志**（如"H-08 属断言写错"） | 数据泄漏，等于把答案喂给模型 | 必然 100% |

另外还发现一个实现级 bug：去注释的正则 `//.*` 把 `https://` 里的 `//` 也切掉了，导致 URL 提取恒为空、"URL 正确"恒为真。

## 二、v2 指标定义

| 指标 | 定义 |
|---|---|
| **严格结构合规率** | JSON 可解析 + 6 个必填字段 + steps 为 ≥2 项数组 + expected ≥10 字 + method 属于预定义方法集 + title ≥6 字 |
| **需求点覆盖率** | 每个功能点定义 5–6 个"必须覆盖的测试点"（如登录的：正确/错误密码、空用户名、空密码、不存在账号、多次失败），按关键词命中计算 |
| **定位器保真度** | 生成代码里的 `By.id`/`By.cssSelector` 与 SUT 真实存在的元素集合比对 |
| **URL 错误脚本数** | 脚本中出现 `example.com` 或非 `localhost:8080` 地址的数量 |
| **可直接运行率** | 同时满足：有类声明 + URL 正确 + 至少 1 个断言 |
| **归因准确率** | 12 条难样本（4 脚本 / 4 环境 / 4 缺陷），日志**只给原始现象不给结论** |
| **误判为缺陷次数** | 真实非缺陷却被判成"系统缺陷"的次数（最危险的一类错误） |

## 三、v2 结果

> ⚠️ **本节是"第一轮 v2"（6 功能点、每模型 3 个脚本）的结果，用于说明收紧度量后的变化；最终数据见第六节**（20 功能点、198 条/轮、10 脚本/模型、24 条归因）。两节的定位器保真度不同，原因是样本量从 3 扩到 10 后排序发生了改变——这本身就是本报告要强调的方法论问题。

| 模型 | 用例数 | 严格结构合规 | 需求点覆盖 | 定位器保真 | URL 错误 | 可直接运行 | 归因(12 难样本) | 误判为缺陷 |
|---|---|---|---|---|---|---|---|---|
| **DeepSeek-V4.1-Flash** | 60 | **95.0%** | 87.1% | 36.4% | 1/3 | **66.7%** | 91.7% | 0 |
| DeepSeek-V4-Pro | 56 | 51.8% | 87.1% | 30.0% | 3/3 | 0% | 91.7% | 0 |
| Qwen-Plus | 58 | 67.2% | **74.2%** | **57.1%** | 3/3 | 0% | 83.3% | 0 |

### 三条结论（有区分度了）

1. **结构化输出能力差异很大**：严格合规率从 51.8% 到 95.0%。v1 的 100% 是被宽松校验掩盖的。
2. **定位器保真度普遍偏低**：本节这版最高 57.1%（3 条样本 + 手写基准，**已被第六节推翻**）；最终以第六节的 21%–25% 为准。
3. **"写得像" ≠ "跑得起来"**：DeepSeek-V4.1-Flash 有 95% 严格合规，但可运行率只有 66.7%；另外两个模型可运行率为 0（编码时用了 example.com 占位域名、或只给裸方法没有类声明）。

### 归因任务（去掉提示后）

| 模型 | 准确率 | 漏判 | 误判为缺陷 |
|---|---|---|---|
| DeepSeek-V4.1-Flash | 91.7% | H-09（把错误码不当判成环境问题） | 0 |
| DeepSeek-V4-Pro | 91.7% | H-04（把评论限流判成脚本问题） | 0 |
| Qwen-Plus | 83.3% | H-04、H-09 | 0 |

**误判为缺陷 0 次**是本次最有价值的结论：三个模型在证据不足时都倾向判"环境/脚本"而不是乱扣缺陷，这对实际测试工作是安全的方向。

### 需求点覆盖的短板（以 DeepSeek-V4.1-Flash 为例）

| 功能点 | 覆盖 | 漏掉的测试点 |
|---|---|---|
| R01 登录 | 4/6 | 不存在账号、多次失败锁定 |
| R02 草稿 | 3/5 | 发布/状态迁移、回收站 |
| R03 媒体 | 5/5 | — |
| R04 评论 | 3/5 | 回复嵌套、垃圾标记 |
| R05 REST | 4/5 | 非法参数 |
| R06 权限 | 4/5 | 删除越权 |

结论：模型擅长"正向 + 明显边界"，**系统性缺口在"状态迁移、回收站、越权删除"这类需要理解业务状态的场景**——这正是人工用例不可替代的地方。

## 五、对报告的写法建议

不要写"三个模型都 100%，说明大模型很强"，那是错的；应该写：

> 在宽松度量下三模型指标均接近满分，但收紧度量后差异显著：严格结构合规率 51.8%–95.6%，定位器保真度 21.1%–25.0%，可直接运行率 0%–65.0%。这说明**"看起来对"与"能跑起来"之间存在巨大鸿沟**，评估大模型的测试产出必须采用可执行性指标，而不是格式合规指标。

### 6.4 结论修订

1. **定位器保真度是三模型的共同短板**：以真实 DOM（1181 id / 193 name / 769 class）为基准、20 条脚本为样本，三模型为 **21.1% / 24.4% / 25.0%**——**四分之三以上定位器是编造的**。指标经过三次修正：样本 3→10→20、基准 手写 22 个 id → 真实 DOM，数字从 30%–57% 一路回落到 21%–25%，每次修正都说明前一版高估了能力。
2. 结构化能力与可运行性必须分开看：合规率 95.6% 的模型可运行率只有 60%，合规率 74.5% 的模型可运行率为 0。
3. **带类声明是低门槛但高区分度的检查**：Qwen 10 个脚本没有一个带类声明，Pro 只有 3 个——这类基础结构问题用一行正则就能筛出来，不需要跑测试。
4. **口径差异必须随表说明**：Flash 结构合规是 3 轮均值±CI，Pro/Qwen 仅 1 轮，属初步观测；脚本类指标三模型均为 n=20 并附 Wilson 95% CI；F06 的 0/10 只能表述为"当前样本下系统性失效"，不能断言模型不支持该类用例。
